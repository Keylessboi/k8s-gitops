# What a new Authentik account gets

Short answer: **the three services you asked about already provision
themselves, and Invidious is the one that cannot.** This file records which is
which and why, because "does a new user get an account here?" is answered
differently by every app and none of them say so on their config page.

Create the user in Authentik, add them to whatever groups gate the
applications, and then:

| Service | New account appears | Mechanism |
|---|---|---|
| **Navidrome** | automatically, on first page load | forward-auth username header |
| **Immich** | automatically, on first SSO login | OIDC `autoRegister: true` |
| **qui** | automatically — there is no account to make | OIDC session only |
| **Invidious** | **one click**: Register, choose a password | no OIDC support exists |
| **Readarr / Calibre-Web** | n/a | forward-auth only, no per-user state |
| **Nextcloud** | on first SSO login | `user_oidc` |
| **Forgejo** | on first SSO login | OAuth source |
| **Vaultwarden** | **blocked** — see below | `SIGNUPS_ALLOWED=false` |
| **remux** | **manual** — no SSO in 0.27.0 | local accounts only |

## The three that work, and how they actually do it

**Navidrome** has no OIDC — the binary contains no OIDC symbol at all. It
instead trusts `X-authentik-username` from a whitelisted source
(`ND_REVERSEPROXYWHITELIST: 10.42.0.0/16`), and `handleLoginFromHeaders` in
`server/auth.go` *creates* the user when the header names one it does not
know:

```go
user, err := userRepo.FindByUsernameWithPassword(username)
if user == nil || err != nil {
    log.Info(r, "User passed in header not found", "user", username)
    ...
    err := userRepo.Put(&newUser)
```

The account it makes has an autogenerated password nobody ever needs, because
the header is the credential. This is also why
`strip-auth-headers-middleware.yaml` exists: any route that does *not* run
forward-auth must delete that header first, or anyone could assert any
username.

**Immich** takes it from OIDC. `autoRegister: true` in the declared
`immich.json` — not the admin UI, because Immich exposes no env vars for OAuth
and clicked-in settings are not in git.

**qui** provisions nothing because it stores nothing. Its OIDC callback puts
`authenticated`, `username` and `auth_method` straight into the session and
never touches a user table. Any Authentik user who completes the flow is in.

## Invidious: why it is a click and not a job

Invidious has never had OIDC. Its only external identity provider was Google,
removed long ago, so there is no API to provision against — and provisioning
directly into its `users` table does not help either, because login needs a
password the new person would then have to be told.

So `registration_enabled: true` stays on, and it is safe *only* because the
vhost runs `authentik-forward-auth`: the registration form cannot be reached
without an Authentik session. **If forward-auth is ever removed from
`apps/invidious/ingress.yaml`, registration must be closed in the same
commit** — otherwise the form is open to the internet.

## The two that need a decision, not a fix

**Vaultwarden** has `SIGNUPS_ALLOWED: "false"` and `DISABLE_ADMIN_TOKEN:
"false"`, which together mean a brand-new person cannot get a vault at all:
the fork treats an SSO login by someone with no prior account as a signup.
Opening it is a deliberate security choice about the highest-value endpoint
here, so it is left as-is rather than quietly flipped. To add someone: flip
`SIGNUPS_ALLOWED` to `"true"` in a commit, have them log in once, flip it
back.

**remux** (0.27.0) has local accounts and no SSO of any kind — one `admin`
user exists. It sits behind forward-auth, so it is not exposed, but a second
person needs an account created by hand in its UI. Worth revisiting when
upstream adds an auth provider; it is young software and this is the sort of
thing that lands.
